# UI — Specification

Source of truth for the UI's internals. The entity spec ([`../../spec/index.md`](../../spec/index.md)) wins on the
cross-subproject contract.

## 1. Built (M0)

- **URLs**: `/<locale>/…` with the ten `LOCALES`; a bare URL redirects to the remembered, browser-preferred or
  default (`en-001`) locale; `/api`, `/auth`, `/_app`, `/assets` are unlocalised.
- **Words in the reader's locale (WL-8)**: `STRINGS` (`src/lib/strings.ts`) is the English source and its key set is
  the contract. Pages and `src/lib` read `TEXT` (`src/lib/i18n.ts`), which answers from the current locale's table:
  `cy-001` has a full Welsh table (`src/lib/strings.cy.ts`), and every other locale reads English for every key. A
  table is typed `Strings` (the shape of `STRINGS`), so a missing or extra key is a type error. The current locale
  is the URL prefix: on the server it is kept per request in an `AsyncLocalStorage` (`hooks.server.ts`), so two
  pages rendered at once keep their own words; in the browser it is `page.data.locale`, reactive, and the root
  layout remounts the page when it changes. A value of `TEXT` must be read when needed, never copied into a
  module-level constant. The Welsh is **machine-written and not reviewed** by a Welsh speaker or a clinician who
  speaks Welsh; `REVIEW` in `i18n.ts` says so (`reviewed: false`, `reviewer: null`), and nothing may call it
  reviewed without a named reviewer and a date. The words least sure of are listed at the top of
  `strings.cy.ts` for the reviewer. Where a section below says "English only", Welsh is the exception: its words
  are those machine-written ones. Words outside `STRINGS` (some `aria-label`s, the API's own 422 problem text, and
  the service's error messages) stay as they are. Tests: `i18n.test.ts` (every key, deep, has a non-empty Welsh
  string that is not English, `{placeholder}`s kept key by key, the review record, a component in `cy-001` and
  `en-001`), `i18n-server.test.ts` (three requests rendered at once each get their own locale), and one Playwright
  test (`/cy-001` in Welsh from the server and after a client navigation, with axe).
- **Security**: strict CSP from `vite.config.ts` (nonces/hashes, no inline style except SvelteKit's own announcer),
  `nosniff`, `DENY` framing, referrer and permissions policies, HSTS over HTTPS.
- **BFF**: `/api/proxy/<path>` forwards GET/POST to `EPR_API_URL` only when the path starts with `api/` and has no
  empty, `.`, `..`, `%` or backslash segment. The browser holds no token.
- **Sign-in (SE-9)**: with `EPR_OIDC_ISSUER` set, `/auth/login` starts the authorization code flow with PKCE (S256, state, nonce)
  against the Keycloak realm; `/auth/callback` checks the state and the ID token's issuer, audience and nonce, and creates a
  session with a fresh random id; `/auth/logout` (POST, same-origin only) ends it here and at Keycloak. The browser holds only the
  `httpOnly`, `SameSite=Lax` cookie `epr_session` (`__Host-epr_session` over HTTPS); tokens stay in the server's in-memory store
  (`src/lib/session.ts`). The proxy adds `Authorization: Bearer`, refreshes within 30 s of expiry, and answers 401 when there is no
  live session. Idle limit 900 s and absolute limit 28800 s (`EPR_SESSION_IDLE_SECONDS`, `EPR_SESSION_ABSOLUTE_SECONDS`). A
  background look (the patient page's minute poll) sends `x-epr-background: 1`; the hook and the proxy do not count it as activity,
  and the header is not forwarded. Two minutes before the idle limit the layout shows an alert with the minutes left and "Stay
  signed in" (`POST /auth/keepalive`, same-origin, 204 or 401, no API call); hazard H-025. `returnTo`
  is a same-site path only. Plain `http://` is accepted only for loopback. Environment: `EPR_OIDC_ISSUER`, `EPR_OIDC_CLIENT_ID`
  (default `epr-web`), `EPR_PUBLIC_URL` (required with an issuer; its origin must be one the client allows).
  **Proxy resilience (CQ-31)**: the proxy gives the API 30 s (`UPSTREAM_TIMEOUT_MS`); a timeout is a 504 and any other
  transport failure a 502, both JSON `{error}`. A token refresh deletes the session only when the provider answers
  `invalid_grant` (or the session holds no refresh token); a network error, timeout, 5xx or malformed answer keeps the
  session and cookie and the proxy answers 503 with `Retry-After: 5`. The proxy forwards `Accepts-version` when it is a short
  token (letters, digits, dots, hyphens) and never touches the path. `X-Forwarded-Proto` is believed only when
  `EPR_TRUST_FORWARDED_PROTO` is `1` or `true`: **a deployment behind a TLS-terminating proxy must set it**, or cookies are
  not `__Host-` prefixed `Secure` and HSTS is not sent.
  **Client address (OS-2, H-049).** The proxy sends the API `X-Forwarded-For` with one entry, the browser's address as
  SvelteKit's `getClientAddress()` gives it (the socket's, or, when adapter-node's `ADDRESS_HEADER` and `XFF_DEPTH` are set
  behind a proxy in front of the UI, that proxy's), and only when it is an IPv4 or IPv6 address. Whatever
  `X-Forwarded-For` the browser sent is never passed on, so the browser cannot choose the address the API sees. The API
  believes it only from addresses in its `TRUSTED_PROXIES`, which must then list the UI server's address (in `compose.yaml`, the UI container's fixed `10.89.240.250`) and nothing a
  browser can reach the API from. The address is personal data: the API records it in `audit_events.network_address`
  and may count it toward a lockout.
- **Pages**: home; `/patients` searches (family-name prefix, birth date, NHS number; an empty search is never sent) and lists up to 50
  matches; `/patients/new` registers, and on a 409 shows each possible duplicate beside the entered record with the matcher's score and
  reasons, registering anyway only with a typed reason (when the 409 says `candidates_cut`, the page adds that only the closest 200 were compared and to search first); `/patients/[id]` shows and edits a record, sending the version it was read at
  (a stale save is reported, never overwritten); `/patients/compare` compares two patients and renders the decision, the score, the per-field
  table and the reasons a link cannot be automatic. A missing similarity renders "not available". The edit form changes only the fields it
  shows and carries every other name, identifier, address and contact detail into the new version.
- **Purpose of use**: the proxy forwards `X-Purpose-Of-Use` only when it is one of the seven codes the API knows; anything else is dropped before it can reach the audit trail. Staff declare theirs in a header picker, **Operations** (the API's default) or **Treatment**, kept for the browser tab only (`sessionStorage`; if storage is blocked the choice lasts until reload). `emergency` is not offered until break-the-glass (SE-3) exists, and `payment`, `research` and `audit` are permitted to no staff role. `/my-record` ignores the picker and sends `patient-access`. Declaring a purpose grants nothing: the API still checks it against the role and records it.
- **My record** (`/my-record`): read-only list of the records linked to the signed-in patient or proxy, from `GET /api/me/patients`. A proxy is told it is a proxy; with no link the page says so; a refusal is announced. No edit form: corrections go through the practice.
- **Who has accessed this record** (on `/my-record`, per record): a button loads `GET /api/me/patients/{id}/access-log` only when pressed, because reading it is itself recorded. Once shown, a form narrows it by first and last day (the patient's own: the browser's time zone, named on the form; each day is sent as the UTC instant it starts at, so a 23 or 25 hour day is right, and the last day is included by sending the start of the next as the API's exclusive `to`), and entries are shown in that zone with the zone named, who (anyone, only me, only others) outcome (all, refused, succeeded) and purpose (any, or one of the seven codes); a day that is not real sends nothing and says so; older entries are asked for under the same filter; Clear goes back to the whole log; a download button gets the log that is showing (its filter, not one still being edited) as `access-log.csv`, up to the 1000 most recent entries, times in UTC; when the API says the file was cut (`x-next-before`, which the proxy now passes on), the page says only the 1000 most recent are in it and to narrow the days. The form's words are in the page's locale (`src/lib/translations.ts`: ar, cy, de, es, fr, hi, zh; machine-written, **not reviewed by any speaker**; English where a word is missing; the Welsh form reads the full Welsh table); the rest of the page is English, or Welsh at `cy-001`. Entries are sentences (`describe` in `src/lib/access-log.ts`): "A member of staff viewed your identity record. Purpose: treatment." Staff are shown by the role and organisation recorded ("A member of staff (clinician, riverside)…"), never by name; words the API sends that the page does not know are shown as given. "Show older entries" follows `next`.
- **Patient banner** (`PatientBanner.svelte`, ID-7): on `/patients/[id]` and each record on `/my-record`, a sticky region labelled "Patient banner" with the name (family name in capitals), birth date and age, sex, NHS number as `943 476 5919`, one other identifier, "No photo held", and the allergy line. The banner shows the record **as stored**, not the form being edited. Age: whole years from a full date (the birthday itself counts), whole months under two years, "about N years" for a partial date, and the "Birth date not recorded" text for an unreadable, future or missing date; never a guess. The photo is fetched through the proxy under the declared purpose (so a patient fetches it under `patient-access`) and shown from an object URL (CSP `img-src` allows `blob:`); the patient page has a Photo section to upload (PNG or JPEG, up to 512 KiB, checked in the page and again by the server) or remove one. The allergy line (hazards H-016, H-018) says one of: the active allergies, high-criticality first and marked, with the risk named and none claimed where it was not stated; "No known allergies (stated <time>)" only when a clinician stated it and nothing was recorded since; "No active allergies are recorded (N inactive). Not confirmed as none known."; "Not recorded in this system. This does not mean there are none."; "Not shown to you for this patient. This does not mean there are none." (403); or "Could not be loaded. This does not mean there are none." Never blank, never "none" without a statement. The patient page makes one allergy call per look and gives it to the banner and to the **Allergy section** (shown only when the call was 200): the list with each status, a form to record one, "No longer applies" and "Entered in error" per allergy, and "Record: no known allergies" or "Withdraw the no-known-allergies statement". `/my-record` fetches under `patient-access` for the banner.
- **Access and consent** (`/patients/[id]/access`, linked from the patient page): two sections. *Care relationships*: the list (kind, the person's token `sub`, in force or ended, dates) with "End relationship" (a PUT with the version seen), and a form to record one (person, kind, optional dates, reason). *Consent*: the list in words ("Deny: receptionist · for any purpose · any record · any label"), "Withdraw" and "Entered in error" per consent, and a form for one provision (deny or permit; roles, purposes, kinds of record and labels as tick-boxes where none ticked means any; optional dates) or the local national data opt-out. The server decides everything: a role that may not (403) gets a message and no form, a stale version (409) reloads the list, a refused record (422) shows the server's reasons. Nothing is deleted.
- **Request limit (OS-2, H-039).** A 429 from the service is passed through the proxy with its `Retry-After`, and `commonProblem(429)` is `rateLimited`: "Too many requests just now. This one was not carried out and nothing was changed. Wait a moment and try again." Every page that asks `commonProblem` shows it, so a refused request is never an empty list or a silent failure. English only, unreviewed wording. Tests: `patient.test.ts`, `proxy-handler.test.ts`.
- **Overdue checks** (`/overdue-reviews`, in the navigation with no count; PX-2, H-048, OQ-PX2): the items of `GET /api/overdue-reviews`, oldest date first, each with the date, a warning when a report of the person's death stands, and a link to the adjustments on the patient's record. A list that is cut says so, and a refusal is said and never reads as none overdue.
- **Reports of death** (`/death-reports`, in the navigation with the count on the home page, the patient list and a patient's record; BV-9, H-046, OQ-BV4): the items of `GET /api/death-reports`, oldest first, each with the time of the report and a link to the patient, and a sentence saying the on-duty clinician is accountable. A cut list says so; a failed load says so and never reads as none.
- **Replies to referrals you sent** (`/referrals`, in the navigation; PC-2, H-044, assumed OQ-PC5): the items of `GET /api/referrals/worklist` (what came back, in words, and when on the site clock), each with a link to the patient and "Mark as seen", which posts the version shown (`POST /api/referrals/{id}/acknowledge`); a 409 means a newer reply arrived or it was already marked, and the list reloads. The navigation shows the waiting count on this page and on a patient's record only (each fetch is audited, and a role without a worklist makes one audited refusal per load there). Says when the list is cut short. Code: `lib/referral-worklist.ts`, `routes/referrals/+page.svelte`. Not built: a count on every page, a reminder for a referral nobody has answered (PC-3), a way to see the reply on this page without opening the patient.
- **Unmatched referral replies** (`/admin/referral-queue`, in the navigation with the open count on admin pages; PC-2, H-044): the open entries of `GET /api/referral-queue` (kind in words, the sender's reference and event, the reasons, no text); "Show the message" loads one with `GET /api/referral-queue/{id}` (note and message as received); clearing is `POST …/{id}/clear` with a reason, and a hand match also needs a referral id (nothing is sent without them); a 409 means someone else cleared it and the list reloads; a list the service says is cut short (`more`) says so. Code: `lib/referral-queue.ts`, `routes/admin/referral-queue/+page.svelte`. Not built: the referrer's own worklist count, a way to open the matched referral from the entry.
- **Refused messages** (`/admin/feed`, in the navigation): the open entries of `GET /api/feed/refusals`; "Show the message" loads one with `GET /api/feed/refusals/{id}` and shows it as escaped text with segments on separate lines; closing sends `POST …/resolve` with an outcome and a required reason (a blank reason sends nothing). A 403 says the role does not allow it; a 409 reloads. No count or alert.
- **Proxy terms** (`/patients/[id]/access`, PA-5, H-011): choosing the relationship `proxy` shows a basis, four scope checkboxes and a required last day (inclusive; sent as the start of the next UTC day); the list shows each proxy's scopes and end, and says plainly when an old proxy has no terms and sees nothing. `proxyTerms` returns null for a date that is not real, so the page sends nothing and the server refuses. The access log words an entry whose roles include `proxy` as "Someone acting as a proxy", not staff. **Not built:** editing a proxy's scopes (end it and record it again), an adolescent rule, a reminder before expiry.
- **Data age** (`/patients/[id]`, EC-12, H-016): under the banner, "Record read at HH:MM" (the last successful read, initial or background). When the latest background look failed, or no read succeeded for 2.5 minutes while the page is open, an alert says the record may not be current and the same record stays on screen. A good look clears it. `src/lib/data-age.ts` is the rule. The same notice is on `/my-record`, which also looks again once a minute and keeps its records on screen when a look fails. **Not built:** the notice on the other pages, a connectivity indicator, offline reading, and sync priority (the CA-7/CA-8 parts of EC-12).
- **Overdue review** (EC-11): on `/admin/break-glass`, a grant the API marks `overdue` starts with "OVERDUE FOR REVIEW"; the flag absent or false shows nothing. Tested in `tests/e2e/patients.spec.ts`. The count shown elsewhere does not yet show the overdue number.
- **Drill record** (EC-10, H-033): when the API says `drill: true`, the banner starts with an alert "DRILL — NOT A REAL PATIENT"; absent or false shows nothing. **Not built:** a label on any list or the tab title (search shows real records only, so no drill record is listed), and a way to register a drill record from the UI. Tested in `tests/e2e/patients.spec.ts`.
- **Temporary identity** (TT-1, H-047): a "Temporary identity" checkbox at registration and on edit (not on search). When the record has it, the banner starts with an alert "TEMPORARY IDENTITY — NOT YET IDENTIFIED", on every page that carries the banner, and patient search marks the row. Unticking it needs a reason; the API's refusal is shown in the reader's language. The banner text and the checkbox are English, or machine-written Welsh at `cy-001` (WL-8), like the rest of `STRINGS`. **Not built:** a mark on the tab title, or on lists other than patient search.
- **Merge** (`MergeSection`, on the patient page, hidden for a merged-away record): the ids merged into this record each with "Undo this merge", and a form to merge another record in (its id and a required reason; the server's refusals are shown in its words). A record merged away shows "THIS RECORD WAS MERGED INTO ANOTHER" in its banner, a link to the surviving record, and no edit forms. Nothing is deleted.
- **Moving between patients** (`/patients/[id]`, hazard H-016): the page is reused when the address moves to another patient (a link to a merged record, say). It clears the previous patient's record, allergies, form, photo choice and emergency-access notice at once, shows "Loading…", and drops any answer (record, allergies, look, save, photo) that is not for the patient now on screen or not the latest asked for. Nothing of one patient is ever shown under another's address.
- **Banner refresh** (`/patients/[id]`): the page re-reads the record when the tab becomes visible and once a minute while it is visible (each look is an audited read, so not more often). A clean form simply catches up. A dirty form (any edit or a reason) is never overwritten: the banner shows the newer record, an alert says "Someone else changed this record (now version N)", the typing stays, and "Reload and discard my changes" is the explicit way to drop it. Saving the old version is still refused by the server (409).
- **Accessibility**: skip link, landmarks, labelled inputs, `role="alert"` on failure, axe (WCAG 2.2 AA) on each page and on the duplicate view.

### Session storage (OS-8)

Sessions live in this process's memory unless `EPR_SESSION_REDIS_URL` is set, in which case `EPR_SESSION_ENCRYPTION_KEY`
(32 bytes, base64) must be set too; half a setting stops startup. In Redis each record is encrypted (AES-256-GCM, bound to
its storage key) and stored under a SHA-256 of the cookie value, so Redis holds no token and nothing that works as a cookie.
Expiry is the record's TTL (idle or absolute, whichever comes first) and a background look does not extend it. A login
attempt is read with `GETDEL`, so it is single-use across replicas. If Redis is unreachable the proxy answers 503 and keeps
the cookie, and the page shows the reader as signed out without deleting anything. Sessions are not counted in Redis, so the
10,000 cap applies to memory only; set `maxmemory` on the Redis. Rotating the key signs everyone out.

## 2. Not built

A shared session store is built but off by default (below); it was not exercised behind two real UI processes. Keycloak-initiated logout; the Keycloak end-to-end
run in CI; patient search,
registration, banner, summary; the clinical pages; the Lily widgets and `DataTable`; translations other than the machine-written Welsh table (and the small tables in `translations.ts`), and any reviewed translation; the inbox; the
portal; dark-theme toggle (colours follow `prefers-color-scheme`).

**Reasons a link cannot be automatic (CQ-38).** The compare and registration pages show each reason from the matcher's `conflict_codes` (nine codes: different NHS numbers, same NHS with different birth dates or names, sound-alike, swapped, extra given name, field unavailable, field below minimum, thin evidence) in the page's locale, with the numbers in the locale's digits (`src/lib/conflicts.ts`). A code, field or number the page does not know shows the matcher's English text for that position; codes missing or a different length from the English list show the English list whole. The wording is machine-written, **not reviewed by any speaker**, and is clinical wording (H-001).

A merge the API refuses as not the same person shows "These do not look like the same person:" and each reason from `conflict_codes`, in the page's locale; if the API sent no codes (a verified NHS number alone decided it) or one it cannot translate, the API's English message shows whole. Machine-written, not reviewed.

**Banner age and the site's zone (RC-9).** The age on the banner is counted on the calendar day in the site's time zone, which the service sends with the patient (`site_time_zone`, from `EPR_SITE_TIME_ZONE`), so every reader at a site sees the same age whatever their own zone; no zone (an older API) or one the browser does not know is UTC. `ageOn(birthDate, now, zone)` and `calendarDay`.

**Site-clock times (RC-9).** A break-glass grant's start and expiry (the patient page and `/admin/break-glass`) the "no known allergies" statement's time and a refused HL7 message's received time are shown on the site's clock with the UTC time beside it, `2026-10-21 09:30 EDT (13:30 UTC)`, from `site_time_zone` (sent by `GET /api/patients/{id}`, `GET /api/break-glass/reviews` and `GET /api/feed/refusals`). With no zone, UTC, or an unknown name the text is the old `2026-10-21 13:30 UTC`. The patient's access log keeps the reader's own zone.

**Referrals (CA-3).** `/patients/[id]` has a "Referrals" section (`ReferralsSection.svelte`, `lib/referrals.ts`) after the vital signs: the list (recipient, priority, state in words, when, the reason and question as text), a form to send one (with an `Idempotency-Key`, OF-1) and, per referral, one button for each event the service lists in `next`. The screen holds no copy of the state table: the buttons, who sends each and whether it needs a note come from the API. A step that needs a note opens its field first. The sender is the referrer and anyone else the recipient (OQ-PC2, assumed), so a button for the other party's step is answered with a refusal, which the page shows (422 list of problems only), not hidden. A cancellation reads "Cancellation requested, not yet confirmed". States whose names are provisional carry a note saying so. Not built: the redirect that creates a linked referral, the unmatched-outcome queue, a patient-facing view, translations (English only).

**Suspicion on a referral (RS-1 to RS-8).** Each referral in the section shows its suspicion, if it has one (`SuspicionView.svelte`, `lib/suspicions.ts`): the condition as text; in bold, when the patient has **not** been told, that the condition must not be named to them; the pathway and version, a note when it is a draft or a newer version exists; any subtype by its list's title, name, code and list; the pathway's priority; the point of suspicion and what the clock starts from; any instruction for the receiving team; each target with its due day in the site's days, marked overdue while open, or as passed at the outcome once ended; the reason when there is no target; the outcome in words, or that it is open until one is recorded; and how many earlier outcomes were entered in error. A 403 and a failed load each say so, never "none". The words are the service's; the screen computes no day. Welsh is machine-written and unreviewed. **Raising one (2026-11-10):** a referral with no suspicion offers "Record a suspicion on this referral" (`SuspicionRaise.svelte`, `buildSuspicion` in `lib/suspicions.ts`), over the newest pathway versions the service sends with the read. It offers only the chosen pathway's band, factors, subtype list and agreement; whether the patient was told has no preselected answer, nor does a required subtype, a band or the agreement, and sending without them names what is missing and sends nothing; the point of suspicion is read in the reader's own time and sent as UTC; the service's refusals are shown as it words them. **Ending and correcting it (2026-11-10):** an open suspicion offers "Record the outcome" (`SuspicionEnd.svelte`, `buildOutcome`): no kind is preselected, confirmed asks for the diagnosis, ruled out for who, every outcome for what it rests on, and it is sent against the version on screen (a 409 reloads); a note says a missed appointment, a decline or a closed referral is not an outcome. An ended one offers "This outcome was entered in error", with a reason, which reopens it, and says an outcome already sent to the PAS is not undone there. **Correcting it (2026-11-10):** an open suspicion offers "Correct this suspicion" (`SuspicionAmend.svelte`, `buildAmendment`): whether the patient was told, the point of suspicion and the instruction, starting from what is recorded, with a reason; the rest of the suspicion is sent as it is, under the same pathway version, against the version on screen; a point left as shown is not moved; nothing changed or no reason is refused before sending. Run once against the real API and Keycloak (2026-11-10, `tests/e2e-keycloak`): recorded, corrected, ended and reopened through the page, the API's history read back. **Not built:** correcting the condition, grounds, band, factors, subtype or pathway on a screen; the version history; a picker for the result a band follows (its id is typed).

**Watch lists (WL-6), on the patient page.** A "Watch lists" section (`WatchListSection.svelte`, `lib/watch-list.ts`) says a watch list is a reminder that sends no results or messages, lists every entry on the record (state in words, since, owner, until, the reason and any end reason, as text), adds the reader to their own list with a required reason and an optional last day (a second active entry is answered "already on your watch list"), and ends an entry with a reason; ending someone else's entry is refused by the service and the page says only the person who added it can end it. A 403 and a failed load each say so, never "none". **My watch list (2026-11-10):** `/watch-list`, linked from the header, lists the reader's own active entries oldest first (since, until, a link to the record), with no reason, since the list carries none; a reason is read on the patient's page. Above it, "Lapsed, not yet closed" lists the reader's entries whose last day has passed, each linking to the record, where a lapsed entry can be ended with a reason like an active one. **Not built:** the owner's name (the token subject is shown); a run against the real stack. Welsh is machine-written and unreviewed.

**Reports of death (BV-1, H-046).** The banner on `/patients/[id]` and its summary shows a line from `GET /api/patients/{id}/death`: a report is marked not confirmed, a confirmed death names its status, and both give the date and say that contact is held. A failed look says so, because silence would read as nothing reported; no assertion shows no line, and no text says the person is alive. A "Reports of death" section (`DeathSection.svelte`, `lib/death.ts`) reports a death and takes a step, each with a reason. The service decides who may do what (OQ-BV2): reception sees the form but not the reasons, and a button a role may not use is refused when pressed, not hidden. "My record" neither asks nor shows anything. English only.

**Needs and reasonable adjustments (PA-6).** `AdjustmentsSection.svelte` on `/patients/[id]` records, checks and ends a need; the page loads them once and the banner reads the same answer, on the summary page too. `lib/adjustments.ts` holds the catalogue, and a unit test fails if it differs from the service's. A failed look is never read as none. See [`spec/reasonable-adjustments/index.md`](../../spec/reasonable-adjustments/index.md).

**Vital signs (RC-6).** `/patients/[id]` has a "Vital signs" section (`VitalsSection.svelte`, `lib/vitals.ts`) after the allergies, loaded from `GET /api/patients/{id}/observations` and reloaded when emergency access opens. Every screen that shows a reading shows both clocks (SW-2): when it was measured and when it was written. A first entry written more than `LATE_AFTER_MINUTES` after its measured time says "late entry" and how late; that says when it was written, never whether it is true. Each entry reads name, value with its unit, where it sits in words, the range given, the measured time on the site's clock with UTC beside it, who recorded it, and "version n" after a correction. The words keep three rules (hazard H-034): a missing value says why (`No value: attempt failed`), never 0 or a dash; a value with no flag says `Not assessed (no range given)`, never normal, and `Within the range given` appears only when the API computed `normal`; the section says in words when there are none, when the role may not see them and when they could not be loaded, each adding that this does not mean none exist. Entries entered in error are collapsed under "Entered in error (n)", struck through, and not in the main list. The form fixes the unit per vital (one unit each, as the service accepts), reads the measured time as the site's wall clock and sends it as UTC (`wallTimeToUtc`; a skipped hour reads as an hour earlier, a repeated hour as the first), refuses an empty or unreadable number in the page so nothing is sent as 0, makes "No value" a separate choice that needs a reason, and shows the API's refusal text whole. English only. Each standing entry has "Mark entered in error": it asks why (required), then sends the stored record unchanged except `status: entered-in-error` with the entry's version (`enteredInErrorRecord`); the entry is kept under "Entered in error (n)", never deleted, and a 409 asks for a reload. Each standing entry also has "Correct": it loads the entry into the form (the vital is fixed, the time shown on the site's clock), needs a reason, and sends a PUT with the whole record and the version it was made from; a critical range the form cannot edit is carried over, not erased. The service keeps the earlier version. Each entry, standing or entered in error, has a "History" button that loads `GET …/observations/{id}/versions` and lists every version oldest first: version, value (a missing value with its reason), where it sits, range, whether it was entered in error, when it was written on the site's clock, who, and the reason (or "no reason given"); it says in words when the role may not see it or it could not be loaded, and closes whenever the list reloads so an old list is never shown beside a change. "Show readings over time" (shown only when something stands) lists one table per vital, in the page's vital order, newest first: measured time on the site's clock, value (a missing value as its reason, a row kept, never 0 or a gap in the list) and where it sits in the service's words (`trends` in `lib/vitals.ts`). Entries in error are left out; every standing reading is listed, none averaged, smoothed, drawn or flagged by the page; a code the page does not know is listed last under its code. **Not built:** a comparison of two versions side by side, a chart, a range or time filter, translations of the section. **Amendment notice (RC-4, H-035).** The list response's `amendment_notices` (by observation id) is shown as a note under the entry it belongs to, in the entry list and in the entered-in-error list: a request nobody has decided, a correction (with the version), or a refusal with its ground and the patient's statement of disagreement, which is shown as text and never as markup. A notice kind the page does not know is still told in general words, and the service's list fails rather than omit one. **Requests to correct a record (RC-4).** `/patients/[id]` has a section after the vital signs (`AmendmentsSection.svelte`, `lib/amendments.ts`) listing the patient's requests from `GET /api/patients/{id}/amendments` with the patient's words (as text), where each stands, and when a decision is due ("overdue" said in words only while undecided). A clinician is offered only the steps that fit: agree, refuse (a ground from the closed list, and a reason), record the correction (the version that carries it), or take the one extension (a reason). Nothing is sent without its reason, ground or a whole version; who acts is the token. 409 and 422 are said in words; a role the service refuses is told so, and "could not load" never reads as "none". **Not built:** a way for the patient to ask, withdraw or state disagreement (no form or screen), the target record shown beside the request (it names the kind only), a check that the version typed is a correction, notices on allergies, any alert, translations (English only, unreviewed wording). Tests: `vitals.test.ts` (5), `amendments.test.ts` (8), two Playwright tests with axe. **The patient's side (RC-4).** Under each record on `/my-record`, `PatientAmendments.svelte` (purpose `patient-access`) lets the patient choose one of their standing vital signs and say what should change, lists their requests with the reading each is about, where each stands and the reason given for a refusal, withdraws one before it is decided, and adds one statement of disagreement to a refusal (kept as written, shown as text). A 403 (a proxy has no scope for amendments) says it is not available, never that the record is correct. Tests: `amendments.test.ts` (3 more), one Playwright test with axe. **Not built:** asking about an allergy, the clinician's list showing the reading a request is about, any alert. **Allergies and naming the record (RC-4).** A patient may ask about an allergy as well as a vital sign (one list, two groups; the request names the kind and the version read); the allergy list shows the notice under the allergy (`AllergySection.svelte`); the clinician's section names the record each request is about (`targetLines`) and says how many wait and how many are overdue, in words, in a status line at the top. A record the role cannot read is not named: the request shows its kind. **Not built:** an alert outside the patient page (nothing tells a clinician who has not opened that patient), asking on a proxy's behalf, reviewed wording. **Patient summary (RC-8, first slice).** `/patients/[id]/summary` (linked from the patient page) is read-only: the banner, the allergies with their amendment notices (entries in error left out), the newest standing reading of each vital sign in the service's words with its notice (`latestReadings` in `lib/summary.ts`; a newest reading with no value is shown as its reason, never replaced by an older value), and a list of what is not built (problems, active medications, immunisations, recent results, upcoming appointments) with the words "This does not mean there is nothing to record." A refused or failed section says so; it never reads as none. Tests: `summary.test.ts` (4), two Playwright tests with axe. **Not built:** the sections above, medication reconciliation, add and edit from the summary, the p95 chart-open performance test, a keyboard-only test, translations (English only, wording unreviewed).
