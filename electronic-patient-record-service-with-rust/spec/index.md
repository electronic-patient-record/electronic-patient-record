| Write and audit in one transaction | `POST`/`PUT` of a patient, a consent or a relationship begin a transaction (`controllers::patients::begin`), write the new version, append the audit row **inside it** (`audit::append` is generic and joins a transaction as a savepoint) and commit. If the row cannot be written, or the commit fails, nothing is stored and the answer is 500; a stale or racing version is rolled back before the refusal is audited. The version-race insert runs in its own savepoint so a lost race does not poison the caller's transaction. The advisory lock is then held to the end of the outer transaction, so the append is the last step. Reads, refusals, `compare`, verify, search and export audit in their own transaction **by design, not as a gap**: they change nothing, so there is no write for the row to be atomic with. What matters for them is ordering and failure, and both hold: the row is written before the data leaves, and if it cannot be written the answer is 500 and nothing is disclosed. (The only thing a shared transaction would add is a consistent snapshot of the data read and the row written, which no rule asks for) | `tests/audit_chain.rs::a_write_and_its_audit_row_commit_or_roll_back_together` (a trigger makes the audit insert fail); by hand through the real-Keycloak suite |
