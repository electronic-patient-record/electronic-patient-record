|---|---|---|
| Login enforcement | On unless `settings.require_auth: false` or `EPR_REQUIRE_AUTH=false`; an explicit env value wins over config | `auth::tests::auth_is_on_by_default` |
| Startup gate | Refuses to start in `production` with login off; or with login on, no keys and no `EPR_PASETO_KEYS_URL` | `auth::tests::startup_gate`; run by hand |
| Keycloak | With `EPR_KEYCLOAK_URL` set, a bearer token that does not start `v4.` is verified against the realm (signature, issuer `{url}/realms/{realm}`, audience, expiry, verified email); the caller is the token `sub`. Half-configured Keycloak, a remote `http://` URL, no audience, or a bad role map: refuses to start | `tests/keycloak_guard.rs` (8, DB-free, local OIDC stand-in); run by hand against Keycloak 26.3.0 under Podman |
| Public paths | `/_health`, `/_ping`, `/_readiness` only | `auth::tests` |
| Fail closed | Before the guard is initialised every non-public request gets 503 | by construction |
| Compare | `POST /api/patients/compare` takes `{a, b}` (matcher `Patient`) and returns a matcher `MatchResult` | `controllers::patients::tests` |
| Audit table | `audit_events`, append-only; action in C/R/U/D/E; outcome in 0/4/8/12; triggers refuse UPDATE, DELETE, TRUNCATE | `tests/audit_immutable.rs` (Postgres) |
| Audit writer | `audit::append` adds a row in its own transaction under an advisory lock; each `digest` covers the previous row's `digest` (keyed MAC via `integrity-mac` when `EPR_INTEGRITY_MAC_KEY` is set, else unkeyed SHA-256, with a startup warning); `audit::verify` recomputes the chain in batches of 1000 by keyset and names the first broken row; `GET /api/audit/verify` (auditor only, purpose `audit` fixed by the endpoint) returns `{intact, rows, keyed, assurance}` (200) or `{intact:false, first_broken_id, reason, …}` (**409**, so a monitor that reads only the status notices), and writes its own audit row `AuditLog/$verify` with the outcome and no row contents. The answer also carries `head` {id, digest}; `?checkpoint_id=&checkpoint_digest=` (both or 400) checks that row still exists unchanged, else 409 at that id, so removed newest rows are detected against a head the operator stored outside the database (nothing stores it automatically). An unkeyed chain can be recomputed by anyone who can write to the database, and the response says which applies | `audit::tests` (6); `tests/audit_chain.rs` (9, Postgres; includes batch boundaries and the endpoint logic): intact chain keyed and unkeyed, edit and delete detected, a recomputed digest without the key detected, 20 concurrent appends do not fork |
| Compare is audited | `POST /api/patients/compare` appends an `E` row (agent = token `sub`, or `anonymous` with login off; detail = decision and score only, never demographics) **before** returning; if the append fails the request fails (500) and no result is returned | `tests/audit_chain.rs`; run by hand with the audit table missing |

| Policy engine (SE-1) | `policy.rs`: roles from the token's `role` attribute (`clinician nurse pharmacist allied-health receptionist clinical-admin patient proxy auditor integrator`; unknown values are dropped) × nine resource kinds × six actions (no delete). `gate` is the route-level check; `evaluate` is the record-level one (care relationship, security labels `R V PSY HIV SUD ETH`, purpose of use, consent, break-the-glass), returning `Allow(obligations)` or `Deny`. Break-the-glass lifts only a missing care relationship, only for a read by a treating role, and never overrides a consent refusal or unmasks a label | `policy::tests` (15, including a matrix of 10 roles × 10 resources × 6 actions × 8 label sets × 5 relationships × 3 consents × 7 purposes × 2 grants = 907,200 requests checked against invariants) |
| Route gate | `authz::authorize_mw` runs after authentication on every request: public paths and login-off pass; a route with no entry in `routes::TABLE` is 403 for everyone; a caller whose roles do not permit the entry's resource and action is 403. Each refusal is audited (outcome 4; route template, method and roles only, never the body) | `authz::tests`, `tests/keycloak_guard.rs` (9), `tests/authz_audit.rs` (3, Postgres); run by hand against Keycloak 26.3.0: clinician 200, auditor 403, no role 403, unlisted route 403, no token 401 |
| Route census | Every served route is public (the three health probes) or in `routes::TABLE`, and every table entry is served | `tests/route_census.rs` (3); fails when the table is emptied |

| Patients (ID-3) | `POST /api/patients`, `GET /api/patients?family=&birth_date=&identifier=`, `GET`/`PUT /api/patients/{id}` over append-only `patient_versions` (+ view `patient_current`). `PUT` carries `expected_version`; a stale or racing write is 409. Search needs at least one criterion, returns at most 50, escapes wildcards. Validation: a family name, a real `YYYY[-MM[-DD]]` birth date, NHS number modulus 11 (other identifier systems kept as given). `X-Purpose-Of-Use` (default `operations`) feeds `policy::evaluate`. Every success and refusal is audited; search and read rows carry no demographics | `patients_store::tests` (4); `tests/patients_store.rs` (7, Postgres); run by hand against Keycloak 26.3.0 |
| Duplicate check (ID-4) | `POST /api/patients` fetches up to 200 candidates sharing an identifier, birth date or family name, scores each with the matcher, and answers **409** with every candidate that is not a `non_match` (record, score, per-field breakdown, conflicts) unless `override_reason` is non-blank. The reason goes in the version history; the audit row lists candidate ids | `controllers::patients::tests` (3); `tests/patients_store.rs::candidates_…`; run by hand |
| Consent (SE-2) | `POST`/`GET /api/patients/{id}/consents`, `PUT …/consents/{consent_id}` over append-only `consent_versions` (`consents_store.rs`; triggers refuse `UPDATE`/`DELETE`/`TRUNCATE`; a stale `expected_version` or a race is 409; withdrawing is a new version with `status: inactive`). A consent is a list of provisions (permit or deny; actor roles, purposes, resource kinds, security labels, a `YYYY-MM-DD` period; an empty list means any) validated on write (unknown role, purpose, resource or label is 422; nothing is silently dropped). `consent::decide` reduces a patient's **current, active** consents to the engine's `Consent` value: a matching deny wins; a permit must name every label on the record, so a general permit never unmasks `SUD`; an unreadable stored provision denies; a deny naming one of a multi-role subject's roles stops the subject. Applied to reads of a patient's identity (`GET /api/patients/{id}` is 403 and audited with the consent ids, never the provisions), to search (hidden results are dropped silently and counted only in the audit row) and to the ID-4 duplicate check (a candidate the registrar may not see is returned as `{"restricted": true}`, still blocking registration). Consent management is for `clinical-admin` (read, create, update) and read-only for `clinician` and `nurse`. `kind: national-data-opt-out` carries no provisions and means a deny for the `research` purpose. Break-the-glass never lifts a consent refusal. |
| Care relationships | `POST`/`GET /api/patients/{id}/relationships`, `PUT …/{relationship_id}` over append-only `relationship_versions` (`relationships.rs`). A relationship ties a token `sub` to one patient as `care-team`, `active-encounter`, `self` or `proxy`, with an optional `YYYY-MM-DD` period; ending it is a new version (`status: ended`); the subject and kind cannot be changed. `relationships::lookup` gives the policy engine the strongest one in force (self, proxy, active encounter, care team, none); an unreadable period withholds. Every patient, consent and relationship route looks it up, so the `patient` role reads and manages only the record it is linked to (with purpose `patient-access`), and a consent refusal does not stop the patient. Only `clinical-admin` records or ends relationships (resource `CareRelationship`): nobody grants themselves access. The service does not check that the `sub` is the patient; that is the administrator's identity check. |
| My record | `GET /api/me/patients`: the records linked to the caller\'s `sub` by an active `self` or `proxy` relationship in force, each passed through the full record decision (role, relationship, consent), so a proxy whose access the patient has refused sees nothing. The purpose of use is fixed at `patient-access`. Care-team links are not listed. One audit row records how many were linked and shown. |
| Interop mappings | `src/interop`, library only (no route reaches it): **`fhir_patient`** (crate `fhir`, R4 only) writes a stored record as a FHIR R4 `Patient` with `meta.versionId`, parsed through the typed model and validated; reads FHIR `Patient` JSON into the identity record, ignores a client-chosen `id`, and **names every top-level element it dropped** (`active`, `maritalStatus`, `photo`...) instead of discarding it silently. **`hl7_adt`** (crates `er7`, `hl7`) reads ADT A01/A04/A08/A28/A31 leniently with `er7` (local `Z` segments and ragged fields are data), reports `hl7::v2` dictionary findings as warnings, maps PID-3 (NHS number by type `NH` or authority `NHS`, other identifiers as `urn:hl7v2:<authority>`, an identifier with no authority is skipped with a warning, never given an invented system), PID-5, PID-7 (partial dates), PID-8, PID-11 postcode and PID-13, leaves an unreadable date or sex blank with a warning, and applies the service\'s own identity rules (`AE` for a bad NHS number or no family name); `acknowledgement` builds `AA`/`AE`/`AR` with `hl7::v2`. **`terminology`** (crate `snomed`) checks that a SNOMED CT code is a valid SCTID (check digit) naming a concept; it does not know whether the concept exists. See `spec/interoperability/openehr-comparison.md` for why the `openehr` crate is not a dependency. |

With login off (development only) there is no subject and the gate stands aside, as authentication does.

## 2. Configuration

`EPR_REQUIRE_AUTH`, `EPR_KEYCLOAK_URL` / `_REALM` / `_AUDIENCES` / `_ROLE_MAP_FILE` (see `operations/keycloak/README.md`), `EPR_PASETO_KEYS` (inline JSON key set), `EPR_PASETO_KEYS_URL`, `EPR_INTEGRITY_MAC_KEY` / `EPR_INTEGRITY_MAC_KEY_FILE` (audit chain key), `EPR_TOKEN_ISSUER`
(default `authentication-service`), `EPR_TOKEN_AUDIENCE` (default `electronic-patient-record`), `EPR_REDIS_URL`
(production cache), `DATABASE_URL`, `PORT`.

## 3. Not built

FHIR `Patient`, phonetic search, any load test of search; the rest of the resource store; FHIR endpoints and the CapabilityStatement; consent beyond identity (SE-2 is built for identity only: no clinical record exists to hide, no export exists to honour consent, the national data opt-out is held locally and no national service is checked, the `research` purpose is permitted to no role so an opt-out changes nothing today, the patient and proxy roles cannot manage consent without a care-relationship lookup, no UI); break-the-glass grants (SE-3: the engine checks a grant but nothing creates,
stores or expires one, and the privacy-officer notification is only an obligation); masking (SE-4: the engine says what to hide,
nothing hides it); break-the-glass and encounter-derived relationships (a relationship is only what an administrator recorded); the record-level `evaluate` is called for patient identity, consent and relationship routes but by no handler for clinical content, because none exists;
the access log for patients (SE-6); an HTTP endpoint to verify the chain (AU-2); audit of 401 responses (only 403s from the gate are audited); refusing to start in `production` without an integrity key (it only warns); adopting a key on a chain that already has unkeyed rows (they would fail verification; set the key before the first write); OpenAPI; rate limiting; CORS allow-list; the search index.
The permission table, label lists and purpose rules are an engineer's first draft, unreviewed by a clinical safety officer or privacy
officer. A valid token whose roles the table permits is enough for the one route there is.
